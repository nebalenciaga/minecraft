# Задание для Grok 4.6: подключить Ubuntu-сервер к облачному ChatGPT/Codex

Документ подготовлен 6 октября 2026 года. Его можно передать Grok целиком.

## 1. Цель и уже выполненные действия

Настрой на сервере владельца официальный **OpenAI Secure MCP Tunnel**, чтобы ChatGPT/Codex в облачном чате мог читать проект и выполнять ограниченную диагностику серверных сервисов через MCP-инструменты.

Владелец уже создал:

- туннель с именем **server germany**;
- ID туннеля: **`tunnel_6ac462a02a7881918261058dd55ca953`**;
- API-ключ для клиента. Значение ключа отсутствует в этом документе и должно вводиться владельцем непосредственно на сервере.

Туннель создан в интерфейсе OpenAI, но установка клиента, подключение MCP-сервера и работа из чата пока не подтверждены. Не считай их выполненными.

Целевой сервер — Ubuntu 24.04. Работай на VPS, который владелец укажет или к которому предоставит текущую SSH-сессию. Путь проекта сначала установи осмотром сервера; не придумывай его и не предоставляй инструменты чтения всего `/`.

Пользователь хочет дальнейшую работу именно из облачного чата. Установка локального Codex на его компьютере не является целью.

### Что этот способ даёт

```text
ChatGPT/Codex → подключение MCP → сервис туннелей OpenAI
                                    ↑
                           исходящий HTTPS с VPS
                                    ↑
                         tunnel-client на VPS
                                    ↓ stdio
                         MCP-инструменты проекта
```

Это доступ к явно предоставленным инструментам. Он не включает обычный SSH из облачного контейнера, не монтирует VPS в `/workspace` и не предоставляет автоматически терминал root.

## 2. Порядок работы

Выполняй установку и диагностику самостоятельно, если у тебя есть доступ к серверу. Если доступа нет, давай владельцу точные команды для его SSH-терминала и анализируй результаты. Не утверждай, что выполнил команды, которые только предложил.

Сначала осмотри сервер и существующую установку, затем подготовь клиент, проверь туннель, подключи инструменты проекта и настрой постоянный запуск. Не останавливайся на работающем тестовом stub: конечная цель — проверенное чтение проекта из нужного облачного чата.

Изменяй только инфраструктуру этого подключения. Сохрани существующие файлы и конфигурацию; не меняй код проекта, lockfiles, БД или действующие сервисы приложения ради подключения. Перед заменой собственной старой конфигурации сохрани её и установи, что именно она обслуживает.

Не запрашивай API-ключ или пароль в чате. Не включай их в команды, историю shell, отчёты, скриншоты, Git или логи. Не используй `set -x`, вывод всего окружения или вывод содержимого файлов с ключами.

## 3. Предварительная проверка сервера

Установи:

1. Версию ОС и архитектуру: `cat /etc/os-release`, `uname -m`.
2. Наличие systemd, свободного места и необходимых утилит.
3. Реальный каталог проекта, его владельца, стек, Git-статус и названия связанных сервисов. Изучай инструкции проекта, если они есть. Не выводи `.env`, приватные ключи и credential-файлы.
4. Наличие уже установленного `tunnel-client`, его версии, процессов и systemd units. Не печатай строки процессов с потенциальными секретами.
5. Свободен ли локальный порт диагностики `18765`:

   ```bash
   ss -ltn 'sport = :18765'
   ```

6. Возможность исходящего HTTPS с VPS к `api.openai.com:443`. Ответ 401 от запроса без авторизации может подтверждать достижимость HTTP-сервиса, но не права на туннель. Не отключай TLS-проверку.

Для клиента туннеля нужны исходящие HTTPS-запросы к `api.openai.com`, включая `/v1/tunnels/*`. Дополнительный входящий публичный порт для туннеля не нужен. Health/UI должны слушать только loopback.

Если проектов несколько и назначение неоднозначно, уточни выбор проекта, продолжая независимую установку клиента.

## 4. Установка официального клиента

Проверенная версия — **v0.0.15**. На машине подготовки документа скачан официальный Linux amd64-архив, проверена его SHA256 и выполнены `--version` и `run --help`. Получена версия:

```text
0.0.15+a390c168ff1b2d14e73a95991c186c6aba3ff5a0
```

Официальные архивы:

- `tunnel-client-v0.0.15-linux-amd64.zip`;
- `tunnel-client-v0.0.15-linux-arm64.zip`;
- контрольные суммы: `SHA256SUMS.txt`.

Для amd64 проверенная SHA256:

```text
8c836dc5d68d68b663d9a5c5b28ff9fa780d9f7a3fffb1c306880b8f32fab5f1
```

Архив содержит `tunnel-client`, companion `cloudflared`, manifest и лицензионные файлы. Сохрани структуру архива. В описанной схеме включать Cloudflare-режим не требуется.

Пример установки от root с сохранением существующей установки:

```bash
bash <<'INSTALL'
set -euo pipefail
apt-get update
apt-get install -y ca-certificates curl unzip python3 python3-venv

case "$(uname -m)" in
  x86_64) arch=amd64 ;;
  aarch64|arm64) arch=arm64 ;;
  *) echo 'Архитектура не поддержана этим примером'; exit 1 ;;
esac

version=v0.0.15
archive="tunnel-client-${version}-linux-${arch}.zip"
base="https://github.com/openai/tunnel-client/releases/download/${version}"
destination="/opt/openai-tunnel/${version}"
staging="$(mktemp -d)"
trap 'rm -rf -- "$staging"' EXIT
cd "$staging"

curl --proto '=https' --proto-redir '=https' --tlsv1.2 -fSL "$base/$archive" -o "$archive"
curl --proto '=https' --proto-redir '=https' --tlsv1.2 -fSL "$base/SHA256SUMS.txt" -o SHA256SUMS.txt
awk -v file="$archive" '$2 == file { print; found=1 } END { if (!found) exit 1 }' \
  SHA256SUMS.txt > selected.sha256
sha256sum --check selected.sha256

unzip -q "$archive" -d unpacked
chmod 0755 unpacked/tunnel-client unpacked/cloudflared
install -d -m 0755 /opt/openai-tunnel
if [ -e "$destination" ]; then
  diff -qr -- unpacked "$destination"
  echo 'Существующая установка совпадает с проверенным архивом.'
else
  mv -- unpacked "$destination"
fi
"$destination/tunnel-client" --version
INSTALL
```

При несовпадении существующей установки останови замену, выясни причину и сохрани старую версию. Не подменяй ожидаемую контрольную сумму, чтобы добиться успеха проверки. При выборе более новой версии сначала заново проверь release assets, целостность и используемые флаги.

## 5. Ключ: права и безопасное хранение

Клиенту нужен **runtime API key** с правами **Tunnels Read + Use** на созданный туннель. Создание ключа само по себе не подтверждает наличие этих прав. Административный ключ для постоянного клиента не нужен.

Официальная страница управления ключами:

https://platform.openai.com/settings/organization/api-keys

Используй отдельный файл `/etc/openai-tunnel/server-germany-api-key`, принадлежащий root с правами `0600`. Ключ вводит владелец в интерактивном SSH-терминале. Следующий блок создаёт новый файл и отказывается перезаписывать существующий:

```bash
install -d -m 0700 -o root -g root /etc/openai-tunnel
python3 - <<'PY'
import getpass
import os
import sys

path = '/etc/openai-tunnel/server-germany-api-key'
if not sys.stdin.isatty():
    # Python читает программу из heredoc; getpass использует /dev/tty.
    try:
        tty_fd = os.open('/dev/tty', os.O_RDWR | os.O_NOCTTY)
    except OSError:
        raise SystemExit('Нужен интерактивный SSH-терминал владельца для ввода ключа.')
    os.close(tty_fd)
key = getpass.getpass('Вставьте runtime API key: ').strip()
if not key or any(c in key for c in '\r\n\x00'):
    raise SystemExit('Пустой ключ или недопустимые символы.')
fd = os.open(path, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
with os.fdopen(fd, 'w', encoding='utf-8') as output:
    output.write(key)
print('Файл ключа создан. Значение не выводилось.')
PY
```

Если файл уже существует, проверь только владельца и права. Не выводи его содержимое. Для плановой замены используй такую же процедуру с новым временным файлом и атомарной заменой после согласованной ротации.

## 6. Первая проверка туннеля встроенными инструментами

Если этот этап уже успешно выполнен, используй его результаты. Для одного ID держи только один активный клиент, особенно при дальнейшем stdio-подключении. Перед переключением останови именно ранее запущенный клиент этого туннеля; не используй широкие `pkill`.

Для начальной проверки запусти от root в отдельной SSH-сессии:

```bash
/opt/openai-tunnel/v0.0.15/tunnel-client run \
  --control-plane.tunnel-id tunnel_6ac462a02a7881918261058dd55ca953 \
  --control-plane.api-key file:/etc/openai-tunnel/server-germany-api-key \
  --embedded-stateless-mcp-stub \
  --health.listen-addr 127.0.0.1:18765
```

Не закрывай эту сессию до окончания проверки. Во второй SSH-сессии:

```bash
curl --fail --show-error --include http://127.0.0.1:18765/readyz
```

Ожидается HTTP 200. При 401/403 проверяй права ключа, организацию и доступ именно к этому ID; не создавай второй туннель автоматически и не выводи Authorization headers.

В ChatGPT открой:

https://chatgpt.com/#settings/Connectors

Добавь подключение с **Connection: Tunnel**, выбери **server germany** или вставь его ID. У подключения должны совпадать workspace и права владельца. Клиент в этот момент должен работать. Включи подключение для целевого облачного чата, если интерфейс требует этого.

Проверь реальный вызов `echo` из чата с новой строкой, например `server-germany-check-2026-10-06`, и совпадение ответа. Самостоятельная симуляция такого ответа на сервере не считается проверкой из облака.

Встроенный режим предоставляет только `server_info`, `echo`, `uppercase`. Он **не предоставляет чтение файлов проекта**. После проверки останови его через Ctrl+C и продолжай настройку настоящих инструментов.

## 7. MCP-сервер для чтения и диагностики проекта

Создай небольшой MCP-сервер отдельно от проекта, например:

```text
/opt/codex-server-audit/audit_mcp.py
/opt/codex-server-audit/venv/
/opt/codex-server-audit/requirements.lock
/etc/codex-server-audit/config.json
/var/lib/codex-audit/
```

Используй официальный Python MCP SDK с stdio-транспортом. Выбери доступную совместимую версию, зафиксируй её и зависимости, проверь установку в отдельном venv. Не меняй зависимости приложения. Не реализуй приближённую имитацию протокола вручную. `stdout` процесса MCP должен содержать только сообщения протокола; диагностические сообщения направляй в `stderr`.

Настрой явный список разрешённых корней по результатам осмотра сервера. Например, псевдоним `project` должен указывать на фактический каталог проекта. В конфигурации должны быть реальные абсолютные пути, а не оставленные шаблоны.

Минимальный набор инструментов:

| Инструмент | Назначение и границы |
| --- | --- |
| `server_info` | ОС, архитектура, версия инструмента, доступные псевдонимы проектов; без переменных окружения и секретов. |
| `list_files` | Список внутри выбранного корня, не более 200 элементов за страницу, управляемая глубина и признак продолжения. |
| `read_file` | Обычный текстовый файл внутри корня; диапазон строк, не более 400 строк и 64 KiB ответа за вызов. |
| `search_text` | Буквальный поиск по допустимым файлам, не более 200 совпадений и 64 KiB ответа; без произвольных параметров утилиты. |
| `git_status` | Состояние конкретного репозитория и при необходимости краткая история; без изменений Git и вывода credential-bearing remote URLs. |
| `service_status` | Состояние только заранее перечисленных units, фиксированные поля: ActiveState, SubState, MainPID, ExecMainStatus. |
| `read_logs` | Ограниченный хвост явно разрешённых журналов проекта; фильтрация секретов, без доступа ко всему системному журналу. |

`git_status`, `service_status` и `read_logs` предоставляй только после проверки применимости и прав. Если проект не использует systemd либо журнал недоступен выбранному пользователю, явно сообщи об ограничении и подготовь подходящий ограниченный источник диагностики. Не выдавай фиктивный успешный ответ.

Обязательные свойства реализации:

- Только чтение. Не предоставляй `exec`, `shell`, запись файлов, перезапуск служб, управление Docker или произвольный SQL.
- Доступ ограничивается конфигурацией, а не аргументами клиента. Блокируй выход через `..`, похожие префиксы каталогов и симлинки. Для открытия используй корневой дескриптор и запрет следования симлинкам либо эквивалентную защиту; простой `startswith` или только предварительный `resolve()` недостаточны.
- Читай только обычные файлы. Не открывай FIFO, устройства и сокеты; ограничивай объём реально прочитанных данных, время поиска и размер ответа.
- Применяй одни и те же исключения к чтению, поиску и обходу каталогов: `.env*`, ключи, credentials, дампы БД, `.git` как произвольные файлы, служебные каталоги с секретами. Шаблоны вроде `.env.example` разрешай отдельно после проверки, что в них нет настоящих значений.
- Не предоставляй доступ к `/etc/openai-tunnel`, `/run/credentials`, `/proc`, SSH-ключам или другим источникам секретов. Маскирование журналов — дополнительная мера; оно не заменяет ограничение источников.
- Для необходимых внешних команд используй фиксированный executable и список аргументов без shell, таймаут и минимальное окружение. Для Git отключи pager, fsmonitor, внешние diff/textconv и optional locks; не применяй `safe.directory=*`.
- Добавь корректные MCP annotations для инструментов чтения, но не считай annotations механизмом ограничения полномочий.

Создай отдельного системного пользователя **`codex-audit`** без sudo и интерактивного shell. Код MCP и конфигурация должны принадлежать root и быть недоступны этому пользователю для записи. Выдай только необходимые права чтения конкретного проекта и разрешённых журналов. Не меняй владельца всего проекта и не применяй `chmod -R 777`. Не добавляй пользователя в группы `docker` или к неограниченному чтению системных журналов ради одного проекта.

Если файлы размещены под `/root` или в закрытом домашнем каталоге, настрой минимальный доступ именно к выбранному проекту. Не предоставляй чтение всего родительского домашнего каталога. Проверь результат от имени `codex-audit`.

Протестируй MCP локальным MCP-клиентом под этим пользователем до включения постоянного туннеля. Не полагайся только на запуск Python без ошибки.

## 8. Постоянный запуск через systemd

`v0.0.15` поддерживает запуск MCP по stdio через `MCP_COMMAND` или `--mcp.command`. Команда запускается как дочерний процесс без shell. В строке не работают shell-подстановки. Для одного tunnel ID должна работать одна такая цепочка процессов.

Пример unit ниже предполагает, что Grok уже создал рабочий MCP-сервер, venv, пользователя и конфигурацию, а процесс `audit_mcp.py` по умолчанию читает `/etc/codex-server-audit/config.json` и запускает stdio MCP.

Создай `/etc/systemd/system/openai-tunnel-server-germany.service`:

```ini
[Unit]
Description=OpenAI Secure MCP Tunnel for server germany
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
User=codex-audit
Group=codex-audit
StateDirectory=codex-audit
StateDirectoryMode=0700
WorkingDirectory=/var/lib/codex-audit
LoadCredential=runtime-api-key:/etc/openai-tunnel/server-germany-api-key
Environment="MCP_COMMAND=/opt/codex-server-audit/venv/bin/python -u /opt/codex-server-audit/audit_mcp.py"
Environment=PYTHONDONTWRITEBYTECODE=1
UnsetEnvironment=CONTROL_PLANE_API_KEY OPENAI_API_KEY OPENAI_ADMIN_KEY
ExecStart=/opt/openai-tunnel/v0.0.15/tunnel-client run --control-plane.tunnel-id tunnel_6ac462a02a7881918261058dd55ca953 --control-plane.api-key file:%d/runtime-api-key --health.listen-addr 127.0.0.1:18765 --log.level info
Restart=always
RestartSec=5
KillMode=control-group
TimeoutStopSec=30
UMask=0077
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=read-only

[Install]
WantedBy=multi-user.target
```

Пояснения для реализации:

- Ubuntu 24.04/systemd поддерживает `LoadCredential` и `%d`. Исходный файл ключа читает systemd; клиент получает ссылку на файл credential. Значение ключа не помещается в аргументы или окружение MCP.
- Это не полная изоляция ключа от дочернего процесса того же UID: поэтому MCP должен запрещать чтение credential-каталогов и не иметь инструмента произвольного исполнения.
- В конечном unit отсутствуют флаги `--embedded-...`: их нельзя совмещать с реальным MCP target.
- `Restart=always` выбран намеренно: завершение stdio child может остановить клиент с успешным exit code. Команда `systemctl stop` всё равно останавливает unit без автоматического перезапуска.
- `ProtectSystem=strict` оставляет приложение и проект доступными только для чтения. Если клиенту нужна запись состояния, используй его собственный `/var/lib/codex-audit`, а не каталог проекта. Проверь совместимость ограничений с фактическим расположением проекта.

Останови прежний тестовый клиент этого туннеля. Затем:

```bash
systemd-analyze verify /etc/systemd/system/openai-tunnel-server-germany.service
systemctl daemon-reload
systemctl enable --now openai-tunnel-server-germany.service
systemctl status openai-tunnel-server-germany.service --no-pager
curl --fail --show-error --include http://127.0.0.1:18765/readyz
```

Существующий unit сначала изучи и сохрани перед заменой. Не перезапускай посторонние службы приложения.

## 9. Проверка настоящих инструментов из облачного чата

После замены stub на реальный MCP проверь/обнови перечень инструментов в подключении ChatGPT. Если интерфейс кэширует старую схему, обнови подключение средствами UI. Не создавай дубли без необходимости.

Выполни из того чата, где должен работать ChatGPT/Codex:

1. Получение списка инструментов и вызов настоящего `server_info`.
2. `list_files` для корня проекта.
3. Чтение существующего несекретного файла, например README или package manifest. Сопоставь фрагмент с содержимым на сервере.
4. Буквальный поиск строки, которая заведомо присутствует в этом файле.
5. Проверку допустимого сервиса/журнала, если соответствующие инструменты предоставлены.

Дополнительная серверная диагностика:

```bash
curl --fail --show-error http://127.0.0.1:18765/health/mcp
journalctl -u openai-tunnel-server-germany.service -n 80 --no-pager
```

Изучи ответы без публикации секретов. Для stdio **HTTP 200 на `/readyz` может появиться до discovery MCP**. Он не доказывает, что инструменты найдены или файл прочитан. Требуются реальный `tools/list` и `tools/call` из облачного клиента; `/health/mcp` служит дополнительным свидетельством обмена с текущим дочерним процессом.

Локальные отрицательные проверки MCP: выход через `../`, внешний симлинк, `.env`, credential-файл, FIFO, слишком большой файл/ответ, неизвестный unit. Во всех случаях должен быть контролируемый отказ или документированное ограничение без утечки содержимого.

Перезапусти только созданный unit, затем повтори чтение из чата:

```bash
systemctl restart openai-tunnel-server-germany.service
systemctl is-enabled openai-tunnel-server-germany.service
systemctl is-active openai-tunnel-server-germany.service
```

Проверь, что старый child завершён, работает один клиент и инструменты доступны после перезапуска. Не перезагружай весь VPS только ради этой проверки.

## 10. Что делать при сбоях

| Симптом | Что проверять |
| --- | --- |
| Ошибка TLS/сети к API | DNS, системное время, доверенные CA, исходящий HTTPS сервера. TLS-проверку сохранять. |
| 401/403 от tunnel API | Runtime key, Tunnels Read + Use, организация и право на конкретный ID; значение ключа не выводить. |
| Туннель не виден в ChatGPT | Workspace туннеля, права подключающего пользователя, состояние клиента; недавнее создание может требовать времени на распространение. |
| Health-порт занят | Определить владельца; выбрать другой свободный loopback-порт и обновить проверки. Не завершать чужой процесс. |
| Виден только `echo`/`uppercase` | Продолжает работать stub либо кэшируется прежний список инструментов. |
| `/readyz` = 200, но tools не работают | Проверить stdio запуск, зависимости, права пользователя, чистоту stdout, discovery и `/health/mcp`. |
| После закрытия SSH всё исчезает | Работал foreground-процесс; проверить постоянный systemd unit. |
| MCP не читает проект | Фактический путь, ACL/права, allowlist и ограничения unit. Не исправлять выдачей root или полного доступа к `/`. |

Не делай серию одинаковых повторов без нового диагноза. Если нужна недоступная настройка аккаунта, сообщи владельцу точное поле/право и продолжай независимую серверную работу.

## 11. Что вернуть владельцу и ChatGPT/Codex

Итоговый отчёт без секретов:

- какой VPS и проект настроены;
- ID туннеля и версия клиента;
- имя подключения в ChatGPT и список реально доступных инструментов;
- разрешённые корни, сервисы и журналы;
- пути конфигурации, имя systemd unit, его состояние и автозапуск;
- результаты локальных проверок и настоящих вызовов из облачного чата;
- ограничения и оставшиеся действия пользователя, если они есть.

Не называй задачу завершённой только из-за созданного туннеля, PID, открытого порта, HTTP 200 на health или работы тестового `echo`. Готовность к анализу проекта подтверждается успешным чтением файла проекта из целевого облачного чата после перезапуска постоянной службы.

Для остановки именно этого подключения:

```bash
systemctl disable --now openai-tunnel-server-germany.service
```

Не удаляй проект, другие туннели или учётные данные при обычной остановке. Удаление инфраструктуры и отзыв ключа — отдельные явно запрошенные действия.
